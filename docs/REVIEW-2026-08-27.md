# GAIN — architecture review, 2026-08-27

A full-stack review of GAIN at commit `43a5b8c`, conducted ahead of two things: opening
the instance to real users, and resuming feature development on top of the finished
nine-phase build.

**Findings only.** Nothing here has been fixed. Each finding carries the evidence that
established it and a recommended disposition; the triage is yours.

## What this review is not

It is not a "does it work" review. `npm run verify` passes clean at this commit —
typecheck, `svelte-check`, ESLint, the control-character check, Prettier, 62 unit test
files and the production build, in CI's order, exit 0. The Playwright suite is 134 tests
across four projects. This is a review of what holds up under new users and new features,
which is a different question.

It is also not a rewrite proposal. The codebase is unusually disciplined: pure-core
separation is real and maintained, the physical-isolation guarantee holds under audit
(F-A3), the OIDC implementation is correct in the details most implementations get wrong
(F-A5), and the commit history shows decisions being revisited with reasons rather than
accreting. Most of what follows is drift, absence, and a small number of load-bearing
claims that are no longer true.

## How to read the severity column

| | Meaning |
|---|---|
| **Critical** | Would cause irreversible data loss or a privacy breach. Fix before real users. |
| **High** | Will actively mislead a user, an operator, or the next agent to touch the code. |
| **Medium** | Real, bounded, and cheaper to fix now than after the next feature lands on top. |
| **Low** | Worth knowing. Defensible to accept, provided the acceptance is written down. |

## Decision records

This is the section you asked for: are the recorded decisions accurate, and does each one
have a reason for existing?

The audit method was to take each decision record as a testable claim about the code and
check it, rather than to read the records against each other. Most of the twelve in
ARCHITECTURE §2 and most of UI-DECISIONS survive that. The exceptions cluster, and they
cluster around one thing: **the plan's symptom framework, which the documents treat as the
app's most safety-critical surface and which the app does not render at all.**

### D1 — The colour triad is reserved for a framework the app never renders

**Severity: High.** UI-DECISIONS §5 opens: "Green, amber and red belong to the plan's
pain-response framework (CONTRACT `safety`, fixture §4) and appear nowhere decorative."
The section then forbids a success-green and an error-red anywhere that could compete with
that scale, and CLAUDE.md restates the reservation as an invariant.

The evidence:

- `--green` is defined in all four theme blocks (`src/app.css:32,59,79,98`) and **used at
  zero call sites** in the entire application.
- `--red` and `--amber` are used at seventeen call sites, and **not one of them is inside
  the session runner** (`src/routes/plan/[slug]/session/[key]/`). They appear in the
  layout, Home, import, export, account, admin and version routes — every one of which is
  a case §5 either carves out as an exception or does not cover.

So the rule reserves three tokens app-wide to protect the legibility of a scale that is
never drawn, and the two amendments recorded as "narrow exceptions" (the celebration
confetti, 2026-08-15; the `/admin` reset control, 2026-08-17) plus CLAUDE.md's later
broadening to "ordinary meanings outside the runner" now describe **the entire practice**.
The exceptions have eaten the rule.

This matters beyond tidiness because the reservation is still charging rent. It is why
there is no success state anywhere in the app, and any future feature that wants one has
to relitigate a decision whose stated justification does not currently exist in the code.

**Disposition — decide which way it goes, then make the record match.** Either the
symptom framework gets built (see D2) and §5 becomes true, or §5 is rewritten to say what
is actually true: red and amber carry conventional destructive/warning meanings outside
the session runner, the runner itself is deliberately colourless, and green is unused.
What should not survive is the current text, which reads as a carefully-reasoned
constraint and describes something unbuilt.

### D2 — `safety.symptom_framework` is stored, exported, and never shown to the user

**Severity: High.** This is the substance behind D1, and it is the more serious half.

The fixture declares a three-level pain-response framework — `green` / `yellow` / `red`,
each with a label, an action (`continue` / `modify` / `stop`) and a list of modifications
(`fixtures/plans/home-training-v1.md:759-780`). It is a first-class part of the contract
(`src/lib/contract/schema.ts:310-322`), it is validated on import, and it is persisted to
its own column (`src/lib/db/schema.ts:69`, written at
`src/lib/db/import-plan.ts:255`) and typed for reading (`src/lib/db/read.ts:33`).

**No UI code reads it.** A search across `src/` for `safety_json`, `symptom_framework` and
`symptomFramework` returns the schema, the import writer and the row type — and no
`.svelte` file, and no route loader.

The consequence is specific. A plan author writes "sharp, escalating, radiating, numbness,
tingling or new weakness — stop", GAIN stores it, replays it verbatim into every export so
the reviewing AI sees it, and never puts it in front of the person doing the movement. The
one moment the guidance exists for — mid-set, deciding whether this sensation is the one
that means stop — is the one moment the app does not show it.

Two things are worth separating, because they are easy to conflate:

- **Symptom *measurement* is built.** The fixture declares `symptoms_during` as a 0–10
  `scale` metric at both set and session scope, the runner prompts for it, and it charts
  under Progress. ARCHITECTURE §10's claim that "symptom and energy tracking come free
  from the metric definitions" is accurate.
- **Symptom *guidance* is not.** The three-level framework is a different object with a
  different shape, and nothing renders it.

Note also that the data models do not line up: the framework has three levels, the
collected metric is a 0–10 scale, and nothing maps one onto the other. A traffic-light
rendering of the metric was never straightforwardly available even if someone had tried.

**Disposition — this is a product decision, not a cleanup.** GAIN carries a health
disclaimer in its README and is about to take real users. Either the framework is surfaced
in the runner (which makes §5 true and gives the triad its job back), or the decision not
to surface it is recorded explicitly, with its reason, so the next person does not read
§5 and assume it exists. Silently storing safety guidance the user never sees is the one
option that should not continue by default.

### D3 — "What this does not decide" names four shipped features as still open

**Severity: High**, because this is the failure mode you named: stale records that slow
down or mislead the next piece of work.

`docs/UI-DECISIONS.md:445-447` closes the document with:

> Still open: the Today/home screen with suggested-next-session, the history and progress
> screens, and the offline sync-state indicator.

All four shipped. Home and the suggested next session, history and progress landed in
phase 7; the sync-state indicator landed in phase 6 with its own timing rule
(`src/lib/sync/banner-gate.ts`) that is itself now a CLAUDE.md invariant. Each has e2e
coverage. An agent that reads UI-DECISIONS end-to-end — which CLAUDE.md instructs it to do
before touching anything user-facing — finishes the document believing four built screens
are greenfield.

**Disposition:** replace the section with pointers to where those decisions were actually
settled, or delete it. It is three lines and it inverts the meaning of the document's
last page.

### D4 — ARCHITECTURE §2 records twelve decisions with no reasons attached

**Severity: High**, and it is the structural version of your requirement that every
decision have a reason for existing.

§2 is the canonical decision list — CLAUDE.md points at it, and calls the twelve
"settled... implement against them rather than relitigating them". It is a three-column
table: number, decision, choice. There is no rationale column, and no prose between the
table and §3.

The reasoning does exist — §1 argues the loop, §3 through §11 justify the individual
choices, §12 explains the toolchain — but none of it is linked from the list, so the list
reads as twelve assertions of authority.

This directly disables the escape hatch the project already wrote for itself.
UI-DECISIONS:15-16 states the rule:

> Where a decision has a *reason* attached, the reason is the part that matters; if a
> future change makes the reason false, the decision is open again.

That rule cannot be applied to any of ARCHITECTURE §2's twelve, because none of them has a
reason attached at the point where they are declared binding. The result is that the
project's most authoritative decision list is also its least revisable one — which is
exactly backwards, and is a large part of why this review was needed.

**Disposition:** add a fourth column, one sentence per decision, or a "why" link into the
section that argues it. This is the single highest-leverage documentation change available,
because it converts twelve unfalsifiable assertions into twelve testable ones.

### D5 — The document's summary of itself is false

**Severity: Medium.** `docs/UI-DECISIONS.md:9-11` states: "Exactly one clause goes
deliberately unbuilt — §3's `2 × N` sub-line, for the reason recorded there."

That was true when written. Given D1 and D2 it is no longer: §5's entire colour framework

The `2 × N` decision itself is fine and should stand — it is well-argued, the reason is

### D6 — Decision 12 understates the deviation kinds actually built

**Severity: Low.** ARCHITECTURE §2 decision 12 reads "Skip / substitute / add sets

### D7 — The contract says `yellow`; the design tokens say `amber`

**Severity: Low**, but it is a rename waiting to bite. The contract's middle symptom level

## Data safety and privacy

The one irreplaceable asset here is a user's logged training history; everything else can
be regenerated or re-imported. This track walked every path that can destroy it, and every
path that could cross the physical-isolation boundary.

The good news first, because it is substantial and it should not be buried: **the
isolation guarantee holds.** See A3 and A5.

### A0 — `control.db` holds emails and plaintext OIDC tokens, and the invariant says it does not

**Severity: High**, and it is the finding closest to Critical in this review. It is also
the one most directly triggered by inviting real users, because it is currently harmless
in a single-user instance and stops being harmless the moment there is a second person.

CLAUDE.md:394-395 states the guarantee:

> The one shared database is `control.db` — the OIDC `sub` → user id mapping and
> server-side sessions — and it stays that way: nothing personal in it, no names, no
> emails.

That is false in two independent ways.

**It holds names and emails.** `extractDisplayLabel` (`src/lib/server/oidc.ts:335-341`)
tries `preferred_username`, then **`email`**, then `name`, and the first non-empty one is
written to `control_user.display_label` (`src/lib/server/control-db.ts:211`, column added
by migration 002 at `:65`). For any Authentik provider that does not emit
`preferred_username`, every user's row holds their email address.

**It holds bearer credentials in plaintext.** The `session` table
(`src/lib/server/control-db.ts:35-45`) stores `access_token`, `refresh_token` and
`id_token` as bare `TEXT`. A refresh token is a live credential: it can mint new access
tokens against Authentik until it expires or is revoked.

Three consequences follow, and each is a decision someone made on a false premise:

1. **The operator sees more than §4 promises.** ARCHITECTURE §4 says the operator "sees
   that a user exists, when they were last active, and how much they have logged." In
   fact `UserStats` carries `displayLabel` and `oidcSub`
   (`src/lib/server/admin-stats.ts:29-31`), so `/admin` shows every user's email (or
   username) and their raw OIDC subject. That is defensible — an operator aiming a
   destructive reset needs to know which account they are aiming at, which is exactly the
   reasoning migration 002's own comment gives — but it is not what the architecture
   document promises, and the gap between the two is where a privacy expectation gets set
   wrongly.
2. **Backups now contain live credentials.** README's backup recipe tells the operator to
   `VACUUM INTO` and copy `control.db` out of the container to the host. Nothing in that
   subsection indicates the resulting file contains refresh tokens, so it will be treated
   with the care its documentation implies rather than the care its contents require.
3. **Breach and retention reasoning is wrong at the root.** Any future thinking about what
   an attacker gets from `/data`, or how long to keep anything, that starts from "nothing
   personal in `control.db`" starts from a false statement.

**Disposition — separate the record from the hardening, and do the record first.** The
invariant must be corrected regardless of whether anything else changes; leaving a false
privacy claim in the file that governs every agent's behaviour is the actual hazard here.
Then, independently, three things are worth deciding on their merits: whether
`extractDisplayLabel` should stop falling back to `email`, whether stored tokens should be
encrypted at rest or dropped when they are not needed (nothing appears to require the
`id_token` after login), and whether the backup recipe should say plainly what it is
copying.

### A1 — A post-commit rename failure leaves a version row pointing at no document

**Severity: Medium.** `importPlan` is careful and correct in its design: the verbatim
document is staged beside its destination, the transaction is `IMMEDIATE`, and the file is
renamed into place only after the commit
(`src/lib/db/import-plan.ts:233`, `:288`, `:292`). If the transaction throws, the staged
file is removed and the tree is untouched — and `tests/db/import.test.ts:261` proves it
with an `ABORT` trigger.

The uncovered direction is the other one. If `fs.renameSync` itself fails — a full disk,
a permissions change, an ENOSPC at exactly the wrong moment — the transaction has already
committed. The `catch` removes the staged file and rethrows, leaving a committed
`plan_version` row whose `source_path` names a file that does not exist.

The blast radius is genuinely small, and the codebase already anticipated it: `readSourceMd`
is a bare `readFileSync` whose failure renders an explanation naming the path rather than a
500, and that was a deliberate choice recorded in the roadmap. So the failure mode is a
version that browses as "the document is missing" rather than data loss or a crash.

**Disposition:** this is fine to accept — but it is currently accepted implicitly. The
"all-or-nothing across two stores" invariant is stated without qualification, and this is
the one gap in it. One sentence in the invariant naming the window is worth more than any
code change.

### A2 — `admin-stats` can open another user's database in write mode

**Severity: Medium.** The module comment is explicit that the `readonly` open is "defence
in depth rather than the guarantee itself", and that the real guarantee is the query
surface. That reasoning is sound. But the fallback at `src/lib/server/admin-stats.ts:83`
opens a foreign `gain.db` **writable** — a documented workaround for a cold WAL database
that cannot create its `-shm` read-only.

Two things follow. The defence-in-depth layer is absent exactly when it is reached, and
the process now holds a writable handle to another user's database inside the one module
whose entire purpose is to never touch their content. Nothing writes through it today.

There is a second, structural half to this, which agent evidence surfaced: **nothing
enforces that `admin-stats.ts` is the only cross-user reader.** The guarantee is described
in CLAUDE.md as "a property of a module boundary rather than a rule", but there is no lint
rule (`eslint.config.js` has no `no-restricted-imports` or equivalent) and no test that
greps for `new Database(` outside the sanctioned files. A second reader added anywhere
dissolves ARCHITECTURE §4 silently.

**Disposition:** the boundary is worth making real, since the document already claims it
is. A restricted-import or restricted-syntax lint rule would convert a convention into the
property it is described as.

### A3 — Physical isolation holds under audit *(validated)*

Every site that opens a database was enumerated. `new Database(` appears in exactly three
files: `control-db.ts:138` (the shared control database), `user-db.ts:65` (reached only
through `openUserDb`), and `admin-stats.ts:80,83` (the sanctioned cross-user reader).

Every one of the ~25 call sites of `getUserDbFor` passes `user.id` or `locals.user.id` —
the identity established by the auth gate. **Not one passes a value derived from a URL
parameter, a form field or a query string.** There is no code path by which a request can
name a database other than its own, which is the strong form of decision 5's promise.

Path traversal at provisioning is closed separately by `USER_ID_REGEX`
(`src/lib/db/user-db.ts:29`), which is tested.

### A4 — Set chronology depends on a client-generated ULID and the device clock

**Severity: Medium.** `set_log` has **no timestamp column at all**
(`src/lib/db/schema.ts`): no `logged_at`, no `created_at`. Chronological order comes from
the ULID primary key, which is lexicographically sortable by its embedded millisecond
timestamp — and which, in the offline design, is generated on the phone.

This is a reasonable design and it is used consistently. The exposure is that a device
with a materially wrong clock produces ULIDs that sort wrongly, and nothing detects or
corrects it. That matters more than it first appears, because CLAUDE.md is explicit that
the export's progress summary is "arithmetic the AI will trust and not check", and that
"'first' and 'latest' must be chronological, not whatever order the rows arrived in". The
summary's correctness therefore rests on the accuracy of a clock GAIN does not control.

A phone that is merely a few seconds off is harmless — ordering within a session is by
`set_no` anyway. The case that bites is a device whose clock is wrong by days, which does
happen after a flat battery or a factory reset, and whose sets then interleave into the
wrong week of the user's history permanently.

**Disposition:** worth recording as an accepted bound with its reasoning, in the same
style as §14's other accepted risks. If it is ever worth closing, a server-stamped
`received_at` written at replay would give a monotonic fallback without disturbing the
offline model — but that is a design decision, not a fix to apply now.

### A5 — OIDC PKCE, state and nonce handling is correct *(validated)*

Checked because it is where self-hosted OIDC implementations usually fail. All three
protections are present and correctly wired: PKCE with S256
(`src/lib/server/oidc.ts:100,124`), a `state` value that is consumed single-use from the
server side via `takeOidcState` (`src/routes/auth/callback/+server.ts:47`) rather than
merely compared, and a `nonce` verified against the ID token claim (`:77`, enforced at
`oidc.ts:279`). The session cookie is an opaque id with an HMAC verified using
`crypto.timingSafeEqual` and a length pre-check
(`src/lib/server/session-cookie.ts:28-31`).

The open-redirect surface on the login round trip is closed and reasoned about
(`safeReturnTo`, `src/lib/server/gate.ts:58-63`), including the protocol-relative `//` and
`/\` cases.

No finding. Recorded so the next review does not re-derive it.

### A6 — The export archive copy fails silently

**Severity: Low.** Every generated bundle is written to `users/<id>/exports/` so that "a
user who loses the paste can find it again"
(`src/routes/plan/[slug]/export/bundle-for-plan.ts:94-98`). The write is wrapped in a
`try`/`catch` whose body is empty and deliberately so — failing the export the user is
about to paste, because an archive write failed, would break the crossing to save a
convenience. That trade is right.

The gap is that the promise is never qualified anywhere the user can see it, and there is
no way for them to discover the copy is missing until they go looking for it. Combined
with C2 — there is no UI that lists these files at all — the feature is currently
write-only storage the user is told about but cannot inspect.

**Disposition:** resolve alongside C2, or drop the archive entirely. It is the only part
of the data directory nothing reads.

## Storage, API and operations under change

This track asked a different question from the others: not "is it correct now" but "what
happens the next time this changes". Two of the answers are reassuring and were worth
measuring rather than assuming.

### C1 — Per-user migrations are lazy, unobservable, and have no reverse

**Severity: High.** This is the finding most likely to hurt during feature development
rather than at launch, and it is a direct structural consequence of decision 5.

Migrations are plain SQL applied in version order, each inside a transaction, tracked in
`_gain_migration` (`src/lib/db/migrate.ts`). That part is clean. The problem is the fan-out:
there is one database **per user**, and `migrate()` runs only inside `openUserDb`, which
is reached only through `getUserDbFor` — that is, only when that specific user's next
request arrives. Startup opens `control.db` and nothing else
(`src/hooks.server.ts:27-29`).

Four consequences:

- **A deploy migrates nobody.** Users migrate one at a time, on their next request, over
  whatever period they happen to log in across. There is no point at which the fleet is
  known to be on one schema.
- **There is no way to see who is on what.** `appliedSchemaVersion` exists and is exactly
  the right function for this — and it is called **only from
  `tests/db/provision.test.ts:40,56`**. No production code path reads it, and the operator
  screen does not show it.
- **A rollback strands the migrated.** Deploy migration 003, some users' databases advance,
  roll the image back, and those users are now running old code against a new schema with
  no down-migration and no detection.
- **A failure is invisible.** If one user's migration throws, that user's requests fail and
  everyone else is fine. Nothing aggregates it; the operator screen shows counts, and a
  user whose database will not open shows as unprovisioned or errors.

There is a second-order version of this in `admin-stats.ts`, which opens foreign databases
**without migrating them** (correctly — it must not write). Its queries are safe against
today's schema, but any future migration that renames or restructures `plan`,
`plan_version`, `workout` or `set_log` breaks the operator screen for precisely the users
who have not logged in since the deploy.

**Disposition:** the lazy model is defensible and probably right for this architecture —
migrating every user at boot would make startup time proportional to user count, and a
household instance does not need it. What is missing is *observability*, and the function
to provide it already exists. Surfacing `appliedSchemaVersion` per user on `/admin` turns
all four consequences above from silent into visible, and is a much smaller change than
switching to eager migration. The rollback question deserves an explicit written policy —
even if the policy is "we don't roll back, we roll forward."

### C2 — Generated exports accumulate on disk forever, invisibly to the user

**Severity: Medium.** Every export writes a copy to `users/<id>/exports/`
(`src/routes/plan/[slug]/export/bundle-for-plan.ts:109-115`) with a timestamped filename.
There is no retention policy, no cap, no rotation, and no route anywhere in the app that
lists, reads or deletes these files.

The size is not trivial. Measured against synthetic data at realistic scale (see C5 for
method), a full-history bundle is 365 KB at one year of training and 1.6 MB at three. A
user exporting on the cadence the loop encourages — once per block, plus retries — writes
one of these per crossing, forever.

The only thing that reads the directory is `directorySize` in `admin-stats.ts:111`, which
counts its bytes into the operator's per-user total. So the user cannot see the files, the
user cannot delete the files, and the operator can see only that this user is somehow
using a lot of disk.

Nothing bounds per-user disk usage anywhere in the app.

**Disposition:** decide what the archive is *for*. If it is a safety net for a lost paste,
it needs a UI and a retention window (last N, or last 90 days). If nothing is going to read
it, deleting the write is the smaller change and removes an unbounded growth path. The
current state — write-only, unbounded, invisible — is the one option that serves nobody.

### C3 — Expired sessions are purged only at process start

**Severity: Low.** `purgeExpiredSessions` is called once, from `startup()`, guarded by a
`started` flag so it runs a single time per process
(`src/hooks.server.ts:21-29`). The container runs `restart: unless-stopped`, so a healthy
instance may not restart for months.

This is not a security hole — sessions are validated against `expires_at` on every use, so
an expired row is inert. It is unbounded growth in `control.db`, at a rate of one row per
login per user, retained indefinitely. With a 7-day idle timeout and real users, that is
slow but genuinely unbounded, and it carries the token columns from A0 along with it:
**every expired session row still holds its plaintext refresh token.**

That last point is what raises this above pure housekeeping. The purge is not just tidying;
it is the only thing that ever removes stored credentials.

**Disposition:** a periodic purge, or a purge on each successful login. The interaction
with A0 is the reason to bother.

### C4 — No rate limiting on any endpoint

**Severity: Medium.** There is no rate limiting, throttling or request-size cap anywhere in
the application — a search for `rate.limit`, `rateLimit` and `throttle` across `src/`
returns nothing, and no reverse-proxy configuration is committed.

The endpoints where this matters are not equally exposed. `/healthz` is public by design
and answers trivially. `/login` and `/auth/*` are public and hand off to Authentik, which
does its own throttling. The one that stands out is **`POST /api/sync`**: it is
authenticated, it accepts a JSON batch of arbitrary length, and it replays every op in one
synchronous transaction. There is no cap on batch size in `syncBatchSchema`, and
`request.json()` is called with no size limit, so a single request's cost is bounded only
by what the client chooses to send.

For a household instance behind a reverse proxy, with users who all had to pass an
Authentik group gate to get in, this is a low-likelihood risk. The reason it is Medium
rather than Low is that the app is single-process and synchronous (C5), so one oversized
batch is one long block for every other user, and nothing anywhere bounds it.

**Disposition:** a batch-size cap in the Zod schema is the cheapest meaningful bound and
belongs to the app rather than the proxy, since it is the app that knows what a plausible
batch looks like. Broader rate limiting is reasonably deferred to the reverse proxy —
provided that gets written down, because right now the app's documentation does not
mention rate limiting at all and neither does the deployment section.

### C5 — Synchronous SQLite does not block the event loop at any realistic scale *(validated)*

Worth testing rather than assuming, because "better-sqlite3 is synchronous and the app is
one Node process" is a legitimate-sounding reason to worry about one user's export
stalling everyone else's session.

Measured directly: the fixture plan imported into a real user database, seeded with
synthetic workouts and sets at four scales, then timed through the actual production path
(`logsForPlan` → `generateExport`).

| Scale | `set_log` rows | DB read | Render | **Total block** | Bundle |
|---|---|---|---|---|---|
| ~4 months | 1,500 | 2 ms | 10 ms | **12 ms** | 162 KB |
| ~1 year | 4,500 | 5 ms | 17 ms | **21 ms** | 365 KB |
| ~2 years | 12,000 | 11 ms | 63 ms | **74 ms** | 862 KB |
| ~3 years | 24,000 | 22 ms | 169 ms | **191 ms** | 1.6 MB |

The heaviest operation in the app blocks for 21 ms at one year of training, and 191 ms at
three years of near-daily logging — and the export is by far the largest read GAIN
performs. Ordinary session-runner writes are single-row.

**Decisions 5 and 9 are validated.** Per-user SQLite in one synchronous Node process is
comfortably adequate for this application's realistic scale, and no amount of user growth
changes that, because the databases are per-user and never queried together. The scaling
axis that would matter is a single user with a decade of history, which the table shows
remains fine.

Also worth recording: better-sqlite3's default `busy_timeout` is 5000 ms, verified
directly. The `VACUUM INTO` backup recipe runs as a second process against the same
database, and that default is what keeps it from failing spuriously against a live writer.
Nothing sets it explicitly, so it is worth knowing that the recipe depends on a library
default rather than on a project decision.

### C6 — "Full history" export size is reported in a unit the user cannot act on

**Severity: Low.** ARCHITECTURE §14 lists "Export outgrows the chat context window" with
the mitigation "windowed by default; pre-computed summary carries the signal". The default
is genuinely windowed (`since_version`), and that mitigation holds for the common path.

The unguarded edge is the `full` option, which `exportWindowOptions` always offers
(`src/lib/export/windows.ts:76`) with no size estimate and no warning. The window picker
shows a workout count per option, and after generation the page reports the result as a raw
character count — "1,703,936 characters"
(`src/routes/plan/[slug]/export/+page.svelte:105`).

Both numbers are honest and neither is actionable. A workout count does not predict a
document size, and a character count does not tell a user whether their chat will accept
it. At the 3-year scale above, "full history" produces roughly 400,000 tokens — beyond
most chat context windows — and the user discovers this after copying, in the other
application, with no indication that a narrower window was the answer.

**Disposition:** low-cost improvement, genuinely optional. Showing an estimated size per
option *before* the choice, or a soft warning above a threshold, would put the information
where the decision is made. Worth noting that this only bites users with years of history,
so it is not a launch blocker.

## Infrastructure, CI and supply chain

Two findings here are launch-relevant. The rest are hardening that can be sequenced.

### E1 — A production build can serve unauthenticated while reporting that it cannot

**Severity: High.** `loadConfig` refuses the dev auth bypass in production, and the refusal
is keyed on `nodeEnv === "production"` (`src/lib/server/config.ts:63,67`). But **`node build`
does not set `NODE_ENV`**, and neither does adapter-node. The guard therefore fires only
when something else sets the variable — which today is exactly one thing, `Dockerfile:43`.

Verified directly against the production bundle at this commit:

```
$ ORIGIN=http://localhost:3911 SESSION_SECRET=… GAIN_DEV_USER=probeuser node build
[gain] ready — origin=http://localhost:3911 … auth=bypass
[gain] AUTH BYPASS IS ACTIVE (GAIN_DEV_USER). Development only — production builds refuse it.
$ curl -o /dev/null -w '%{http_code}' http://localhost:3911/
200
```

The request is served without authentication, and the process states on the line above
that production builds refuse to do this.

Calibration, because it matters for how you sequence the fix: the documented Docker
deployment is **safe** — the Dockerfile sets `NODE_ENV=production`, and with it set the
guard works correctly and startup throws as intended. The exposure is anyone serving with
`node build` directly, which README and CLAUDE.md both present as a supported way to run
the app, with a `GAIN_DEV_USER` left in their shell or `.env`.

What makes this High rather than Medium is not the likelihood — it is that the warning
message actively asserts a protection that is not in force. An operator reading
"production builds refuse it" on a server they are serving from `node build` draws exactly
the wrong conclusion.

**Disposition:** the guard needs a signal it can trust that is not `NODE_ENV` — the
presence of real OIDC configuration, or an explicit opt-in variable, rather than the
absence of a variable nothing sets. At minimum the warning should not claim a refusal it
is not performing.

### E2 — No Content-Security-Policy, and no security headers at all

**Severity: High** in the sense of "should be closed before real users", **Low** in
exploitability for this deployment shape.

`svelte.config.js` has no `kit.csp` block, `hooks.server.ts` never touches response
headers, and a search for header-setting across `src/`, `svelte.config.js` and
`vite.config.ts` returns nothing. Confirmed empirically against `node build`: an HTML
response carries `content-length`, `content-type`, `etag`, `link` and `x-sveltekit-page`,
and none of `Content-Security-Policy`, `X-Frame-Options`, `X-Content-Type-Options`,
`Referrer-Policy`, `Strict-Transport-Security` or `Permissions-Policy`. SvelteKit and
adapter-node set none of them by default.

Nothing in `README.md` or `docs/` tells the operator to set them at the reverse proxy
either, so the omission is total rather than delegated.

The practical consequence is bounded — the app is same-origin, has no user-generated HTML,
and every user passed an Authentik group gate — but `/admin`'s reset control and the
session runner are both framable, and any future XSS has no backstop.

**Disposition:** SvelteKit has first-class CSP support via `kit.csp`, and it handles the
nonce/hash plumbing for inline styles that would otherwise make this painful. This is the
cheapest large security win available. Decide deliberately whether the remaining headers
belong in the app or at the proxy, and write the decision down either way.

### E3 — `main` is unprotected, and nothing runs on a push to it

**Severity: High**, because it is the assumption the CI design rests on.

`ci.yml` runs on `pull_request` and on `v*` tags. A plain push to `main` triggers nothing,
and the workflow comment states the reasoning: "every commit that reaches `main` was
already vetted by its PR."

That premise is not enforced. The GitHub API reports no branch protection
(`branches/main/protection` → HTTP 404 "Branch not protected") and no rulesets
(`rulesets` → `[]`) on a public, forkable repository. Nothing requires a PR, a review, or a
green check before code lands on the branch that releases are cut from.

**Disposition:** this is a repository settings change, not a code change, and it makes an
existing design decision true instead of aspirational. A tag is also currently cuttable
from any commit, with no check that it is an ancestor of `main`.

### E4 — `/healthz` verifies nothing, so a broken container reports healthy

**Severity: Medium.** `src/routes/healthz/+server.ts` returns `{ status: "ok" }` and
touches nothing. `isPublicPath` short-circuits before any database access, and `startup()`
is `started`-guarded, so after boot the endpoint exercises no dependency at all.

Verified by making the data directory unwritable under a running server:

```
healthz          HTTP 200
page (new user)  HTTP 500
```

Both the Docker `HEALTHCHECK` and Portainer poll this endpoint, so a container whose
storage has failed is never restarted and never alerts.

One nuance worth recording, found while verifying: already-active users can keep working
through a storage failure, because their database handle is already cached in the
process-wide map (`src/lib/server/app-state.ts:25`). So the failure presents as *new and
uncached users breaking while existing sessions continue* — which is harder to notice, not
easier.

**Disposition:** a health check that opens `control.db` and runs `SELECT 1` would catch
the whole class. Keep it cheap and keep it unauthenticated.

### E5 — Nothing tracks dependency currency, and the audit has a blind spot

**Severity: Medium.** The stated policy (CLAUDE.md, Stack) is that every dependency runs
on a current major. Nothing enforces it and it has already drifted: `npm outdated` reports
TypeScript at `6.0.3` against a latest of `7.0.2` — a full major behind the policy the
document asserts.

There is no `dependabot.yml`, no `renovate.json`, and Dependabot is disabled at the
repository level (`vulnerability-alerts` → HTTP 404, `dependabot_security_updates:
disabled`). CI has no `npm audit`, no image scan, no CodeQL, no SBOM and no provenance
attestation.

The blind spot is worth stating precisely, because it will mislead: `npm audit
--omit=dev` reports **zero** vulnerabilities, while `npm audit` reports three (all one
advisory — `cookie` &lt; 0.7.0 via `@sveltejs/kit`, with no fixed version available
upstream). `@sveltejs/kit` is a devDependency, but adapter-node **inlines it into the
server bundle**, so the vulnerable code ships in the runtime image while the production
audit reports it clean. Any future advisory in a bundled devDependency will be invisible
the same way.

Positives: secret scanning and push protection are both enabled, and no secrets are tracked
in git.

**Disposition:** Dependabot or Renovate is the fix for the policy drift and costs one file.
The audit blind spot is a reason to run plain `npm audit` rather than the `--omit=dev`
variant, and to treat the result as advisory rather than gating, given the current
unfixable advisory.

### E6 — No structured logging, no metrics, no error reporting

**Severity: Medium**, and it is the one that will hurt most when a real user reports a
problem you cannot reproduce.

`src/lib/server/log.ts` is the entire logging layer — one function wrapping
`console.error` — and it has **one call site in the application**
(`src/routes/account/+page.server.ts:69`). There is no custom `handleError` hook, so every
unhandled server error falls through to SvelteKit's default `console.error(error)`.

What an operator actually gets is a raw stack trace against minified bundle paths, with no
timestamp, no user id, no request id, no correlation to the status line above it, and ANSI
colour codes embedded in the stream. There is no request log, no metrics endpoint and no
error aggregation. "How many users hit an error today" and "which user lost a workout" are
both unanswerable.

**Disposition:** a `handleError` hook that attaches a request id and the user id, plus a
one-line-per-request log, would be a small change with a large operational return. This is
worth doing *before* real users rather than after, because the first incident is exactly
when you cannot add it retroactively.

## UI, accessibility and test coverage

The session runner is the best-built surface in the app and largely clears this bar: all
five modal overlays carry `role="dialog"`, `aria-modal`, `aria-labelledby`, a focus trap
and Escape handling, and `svelte-check` reports zero errors and zero warnings with no a11y
rule suppressed anywhere. The findings below are things the compiler cannot see.

### U1 — The symptom scale's selection is invisible to a screen reader

**Severity: High.** `MetricRow.svelte` renders scale, number and enum metrics as a row of
buttons whose selected state is carried **only** by CSS:

```svelte
<button type="button" class="scale-cell" class:selected={selected === value}>
```

with `.scale-cell.selected { background: var(--accent-soft); border-color: var(--accent) }`
(`src/lib/components/MetricRow.svelte:66-71,145-148`). There is no `aria-pressed`, no
`role="radio"` with `aria-checked`, and no non-visual indicator of any kind.

The group itself is well-formed — `<fieldset><legend>` gives it an accessible name — so a
screen-reader user can hear the question and the available values, and cannot determine
which one they have selected.

This is not a peripheral control. It is the input for the 0–10 symptom scale, and it is
used in the pre-session gate, the wrap-up sheet and the next-morning prompt. In a health
adjacent app, "which pain score did I just record" is precisely the thing a user must be
able to confirm.

**Disposition:** `aria-pressed` on each button is a one-attribute fix and is the correct
pattern for a toggle-style selection. Whether this blocks opening to users is your call
and depends on who they are — but it is the single highest-value accessibility fix in the
app, and it is very cheap.

### U2 — A cancelled correction leaves a value that was never logged in the input

**Severity: Medium**, and it is a genuine correctness bug rather than a polish item.

`LogStrip.svelte` holds per-slot input drafts in a `SvelteMap` keyed on `slot.key`, and the
displayed value is `draft.reps ?? asText(prefill.reps)` — so a draft **shadows the
pre-fill** (`src/routes/plan/[slug]/session/[key]/LogStrip.svelte:71-76`). That shadowing
is deliberate and documented: an adjustment should survive looking at another exercise and
coming back.

The problem is that nothing ever removes an entry. Searching the file for `edits` returns
exactly three references — the declaration, the read, and one `edits.set` — and no
`delete`, no `clear`. `LogStrip` is not inside a keyed block, so it never remounts either.

The reachable sequence: tap a logged ledger row to correct it, change reps from 10 to 99,
tap **Cancel**. Nothing is written and the ledger correctly still shows 10. Tap the same
row again and the strip offers **99** — a number that was never logged, presented as the
current value, one effort tap away from being committed.

This sits right against a stated invariant. CLAUDE.md holds that "client state is what was
submitted, never what was pre-filled"; the ledger honours that, but the input strip can now
offer a third thing that is neither. There is no test on this path — the correction flow
has no e2e coverage at all.

**Disposition:** clear the slot's draft on both a successful submit and a cancel. The
deliberate cross-exercise persistence is worth keeping; it is the cancel and post-commit
cases that need the entry dropped.

### U3 — `/import`'s failure screens have no coverage of any kind

**Severity: High**, because it is the one place a stated invariant is protected by nothing.

CLAUDE.md holds that "every failed import produces a pasteable report — not just contract
violations", and that a user's recovery from a bad import is pasting the error back into
their chat. The parser side of this is genuinely well covered: all seven
`ParseFailureKind` variants have tests, malformed YAML included
(`tests/parse.test.ts:99-163`).

The *screen* has nothing. There is no e2e test that renders a parse failure, the
pasted-bundle explanation (a UI-DECISIONS §11 requirement), or the blocking-revision
report. And `blockingReport()` — which assembles an AI-facing report by string
concatenation — lives inside `src/routes/import/+page.svelte:79-87`, so no unit test can
reach it either.

The result is that the user's entire recovery path from the most likely failure in the
whole loop is unverified end to end.

**Disposition:** extracting `blockingReport` into `$lib` makes it unit-testable, and one
e2e that pastes a broken plan and asserts the report is copyable would close the invariant.
This is a roadmap item rather than a one-line fix.

### U4 — A vacuous chart assertion, of exactly the kind phase 7 already fixed

**Severity: Medium.** `e2e/progress-walkthrough.spec.ts` internalises the phase-7 lesson
twice in comments — the volume and duration charts are asserted on `rect` and `.dot`
specifically so that a rendered-but-empty chart cannot pass — and then breaks it at
`:112-114`, which asserts only that the metric-detail `svg[aria-label=…]` is visible.

`Sparkline.svelte:54` renders that `<svg role="group" aria-label>` in **both** the
populated and empty branches; the empty state is a `<text>` element inside the same svg.
The assertion therefore passes with zero data points, which is the precise failure the two
assertions above it were rewritten to avoid.

Two weaker instances are worth knowing rather than fixing: `.log-strip` and
`.exercise-status` also render unconditionally, and `expect(page.locator(".log-strip"))
.toBeVisible()` is used as the "runner is ready" signal in nine specs — it would pass on a
fully-logged, un-loggable strip.

**Disposition:** assert on `.dot` like its siblings. One line, with a named precedent.

### U5 — UI-DECISIONS §12 over-claims what is mechanically checked

**Severity: Medium**, and it belongs to the decision-accuracy theme as much as to testing.

§12 states that every screen is checked at three viewports "in both themes", and that
"everything interactive is at least 44 px". The first half is substantially true for
overflow: `assertNoHorizontalOverflow` has 28 call sites and covers the runner, its four
overlays, Home, export, progress, history, versions, admin and account at all three
viewports.

The claims that do not hold:

- **Both themes** is delivered on three screens (`session-runner-theme`,
  `admin-walkthrough`, `account-reset-walkthrough`), and the runner theme spec pins itself
  to 360×800 and skips the other two projects. The light palette is never rendered at 390
  or 768 anywhere, and never at all on home, import, export, progress, history or versions.
- **44 px** is asserted nowhere. `min-height: 2.75rem` is applied across the runner and
  metric rows, and is absent on `/admin`, `/account`, `/export`, `/import` and the layout
  chrome, which use padding with no floor.
- **`/import` has no overflow check at all** — the largest unchecked surface, and the one
  whose shape (full-width `<select>`s, `<details>` groups, a warnings panel) most invites a
  360 px break.

`ActivitySheet` and `NextMorningPrompt` are also both dismissed before the overflow
assertion runs, so they are checked only in their absent state.

**Disposition:** two options, and they are genuinely different decisions. Either narrow §12
to describe what is actually enforced, or extend the suite to match the claim — a
touch-target sweep is the same shape of assertion as the overflow one and catches the same
class of desktop-invisible bug. What should not persist is a document that asserts
mechanical enforcement that does not exist, since the whole point of §12 is that this
category cannot be caught by eyeballing.

### U6 — No component tests exist, and some logic is only reachable through a browser

**Severity: Medium.** Confirmed: 60 test files, zero of which touch a `.svelte` file, and no
DOM tooling in `devDependencies` (no jsdom, happy-dom, or `@testing-library/svelte`).
`vitest.config.ts` sets `environment: "node"`. All 7,388 lines of Svelte are covered
exclusively by Playwright.

The large components are mostly **not** the problem, and this is worth saying because the
line counts invite the opposite conclusion: the 811-line session runner page delegates
nearly every decision to tested `$lib` modules, and `ExerciseCard` is 145 lines of script
against 200 of CSS. The pure-core discipline is real.

What has leaked into components is small and specific:

| Location | Logic | Why it matters |
|---|---|---|
| `LogStrip.svelte:93-108` | `step()` stepper arithmetic and float-noise rounding; `parseNumeric()` | Produces `weight_kg`, which is a stated invariant. Pure, ~15 lines, no test |
| `import/+page.svelte:79-87` | `blockingReport()` | See U3 — an invariant assembled in an untestable place |
| `session/[key]/+page.svelte:509-531` | `applyHydration()` merge of server state and local ops | `hydrateSession` is tested; the merge and cursor move are not |
| `account/+page.svelte:24-30` | `clearWorkoutStorage()` | Its own comment says a surviving key makes the runner skip writing a `start` op |

`focus-trap.ts` already demonstrates the right pattern — it splits the pure
`nextTrapFocusTarget` out and unit-tests that half. It is applied nowhere else.

**Disposition:** moving these four into `$lib` is a small, mechanical change that removes
most of the argument for adding component-test tooling at all. Prefer that to introducing
jsdom.

## Invariant enforcement

CLAUDE.md's Invariants section is the project's most load-bearing document — it is what
stops each new agent re-deriving the same hazards. Every claim in it was checked against
the test suite to establish whether a test would actually fail if the invariant were
violated.

**The headline is good.** The majority are genuinely asserted, several unusually well:
`context_md` byte-identity is covered at all three hops; the `(scope, key)` metric rule is
asserted on per-row values rather than row counts, so a merge would be caught; the
`set_log` `isCorrection` rule is proven by two fresh non-correction logs producing two
rows; rename-carries-history has both unit and e2e proof; and the export summary's
arithmetic — per-set load, chronological ordering under shuffled input, and `|` escaping
verified by counting delimiters — is thoroughly covered.

Four gaps are worth acting on.

### I1 — The quarantine path is proven only against a test double

**Severity: High.** This is the highest-stakes coverage gap in the codebase, because
CLAUDE.md is explicit that an invisible quarantined op "is exactly the data loss this whole
phase exists to prevent, just moved one step later."

`tests/sync/queue.test.ts:62` proves that a quarantined op leaves `pending` and survives —
but it exercises `tests/sync/memory-outbox.ts`, a hand-written double built to behave
correctly. The code that actually runs on the phone, `src/lib/sync/idb.ts`, has **no unit
test** (its own comment defers to e2e), and **no e2e spec ever produces a quarantine** — a
search across `e2e/` for "quarantin" finds one comment and zero assertions.

So both failure modes the invariant names are reachable with a fully green suite: if
`idb.ts`'s `quarantine()` deleted the record instead of updating its state, that is
"dropped"; if `pending()` stopped filtering on state, that is "retried forever, blocking
everything behind it". And `bannerText` being correct proves nothing about the banner being
*rendered* from a real quarantined record.

**Disposition:** one e2e that syncs an op naming a removed exercise slug, then asserts both
the surviving IndexedDB record and the visible banner, closes the whole gap.

### I2 — `client_id TEXT UNIQUE` is documentation, not a test

**Severity: Medium.** The DDL is correct on all five tables the sync layer writes
(`src/lib/db/schema.ts:202,215,227,239,249`), but **no test reads the DDL**, and
idempotency is achieved in application code by `selectByClientId`-then-insert. Dropping the
constraint therefore breaks nothing in the suite — every idempotency test still passes,
because none performs a raw duplicate insert or expects a `SQLITE_CONSTRAINT`.

The forward-looking half is the sharper risk. The invariant explicitly says "any new log
table needs one", and nothing whatsoever enforces that. A sixth table added without
`client_id` looks correct until the day a queue replay doubles somebody's history.

**Disposition:** a ~10-line test reading `sqlite_master` and asserting `client_id TEXT
UNIQUE` on each of the five tables makes it structural, and fails loudly the day a sixth
appears.

### I3 — Nothing keeps `docs/CONTRACT.md` and the Zod schema in sync

**Severity: High**, given what CONTRACT.md is. It is shipped output, reproduced verbatim in
**both** outbound templates, so it is the instruction set every AI receives.

The only test touching it asserts that it is *embedded verbatim* in the templates — never
that its content matches the schema. The "minimal valid block from CONTRACT §6" at
`tests/schema.test.ts:14-38` is a **hand-copy**, not read from the file.

So the three-places rule is pure convention. Edit CONTRACT.md's spec without touching the
Zod schema and the entire suite passes — GAIN then ships instructions telling every AI to
emit something its own parser rejects, and the user's only recovery is pasting the
rejection back into a chat that was following GAIN's own document. The schema↔fixture half
*is* effectively coupled, since six test files parse the fixture through `contractSchema`,
so that direction fails loudly.

**Disposition:** extract CONTRACT §6's minimal block from the file at test time and parse
it through `contractSchema`, replacing the hand-copy. That catches the direction that
actually hurts, and it is a small change.

### I4 — "Counts, never content" is two substring checks, and the module boundary is not one

**Severity: Medium.** `tests/server/admin-stats.test.ts:62` asserts that the serialised
stats contain neither `"Home"` nor `"goblet"` after seeding the fixture. That catches a
plan-name or slug leak from one fixture. It would not catch a leaked workout note, a
`MAX(weight_kg)`, a session key, a metric value or a deviation reason — adding a `notes:
string[]` field to `UserStats` passes the suite.

The more serious half is structural and connects to A2: CLAUDE.md describes the single
cross-user reader as "a property of a module boundary rather than a rule", and **nothing
makes it a boundary**. There is no `no-restricted-imports` or restricted-syntax rule in
`eslint.config.js`, and no test greps for `new Database(` outside the sanctioned files.

**Disposition:** a lint rule restricting `better-sqlite3` imports to the three files that
may hold them converts the description into the property it claims to be. A type-level
allowlist over `UserStats` fields would do the same for the content half.

Two smaller notes: the `IMMEDIATE` qualifier on the import and replay transactions is
enforced by nothing — changing `.immediate()` to a plain transaction fails no test — and
the rename-before-upsert ordering is caught only incidentally, by a test that does not name
the ordering as its subject.

## What I would do, in what order

Sequencing advice, not a plan — the triage is yours. The grouping reflects that two of your
goals pull in different directions: some of this protects users you are about to invite,
and some of it protects the velocity of the features you are about to build.

**1. Correct the false statements first, before any code.** A0's privacy claim, D3's
"still open" section, and D4's missing reasons are all documentation changes measured in
minutes, and every one of them is currently capable of causing someone — you, or an agent —
to make a wrong decision confidently. A false invariant is worse than a missing one,
because it is load-bearing in reasoning without being load-bearing in code. This is also
the cheapest possible answer to the concern that started this review.

**2. Then the launch-gating handful.** E1 (the bypass guard), E2 (CSP), E3 (branch
protection) and U1 (`aria-pressed`) are all small, self-contained, and each closes
something that gets materially worse the moment a second person has an account. E3 is a
settings change; U1 is one attribute.

**3. Then decide D1/D2 deliberately, because it is a product question.** Whether GAIN shows
a plan's symptom framework to the person training is not a cleanup task, and it should not
be resolved by whoever next edits `app.css`. It governs what the colour system is *for*,
and until it is answered the reservation keeps constraining designs for a reason that does
not currently exist. Answer it, then make §5 true either way.

**4. Then the two coverage gaps that guard invariants nothing else guards** — I1 (the real
quarantine path) and I3 (CONTRACT ↔ schema). Both are small, and both currently sit under
claims the project relies on being true.

**5. C1 before the next schema change, not after.** Surfacing `appliedSchemaVersion` on
`/admin` is a much smaller change than the incident it prevents, and the function already
exists. This is the finding most likely to bite during feature work rather than at launch.

Everything else is genuinely triageable. E6 (logging) is the one I would pull forward out
of that group, on the grounds that the first user-reported bug you cannot reproduce is
exactly when you will wish it had been there.

## A closing note on the codebase

It is worth stating plainly, because a findings-only document reads more negatively than
the evidence warrants.

The disciplines this project set for itself are real and are being kept. The pure-core
separation holds — the large components delegate to tested `$lib` modules rather than
accumulating logic. The physical isolation guarantee survives a deliberate audit. The OIDC
implementation is correct in the specific details that self-hosted implementations
routinely get wrong. The export summary's arithmetic — the thing CLAUDE.md correctly
identifies as "arithmetic the AI will trust and not check" — is among the best-tested code
in the repository. `npm run verify` and CI run identical checks in identical order.

The failure mode this review actually found is a specific and fairly narrow one: **the
documentation is extensive enough, and authoritative enough, that it has started to
describe intentions rather than the code.** Nearly every High finding is a gap between a
confident statement and a fact — the colour rule, the privacy invariant, the bypass
warning, the "vetted by its PR" premise, the mechanically-checked viewport claim. The code
is in better shape than the documents that describe it, which is an unusual and much more
tractable problem than the reverse.
